# Sell verified fixes, not shared memory

The opening is real but narrow. No shipping product today maps a **normalized coding-agent error signature to a fix that tests or CI have verified**, works across repositories and vendors, and has enterprise-grade provenance and access control. Every major agent vendor now runs an automatic memory layer, but each keeps it inside its own walls. GitHub Copilot Memory comes closest, and it is scoped to one repository and one vendor ([GitHub blog](https://github.blog/2026-01-09-building-an-agentic-memory-system-for-github-copilot)). Claude Code's auto memory deliberately skips "debugging fixes" ([Claude Code docs](https://code.claude.com/docs/en/memory)). The research literature backs reuse with conditions attached. Distilled experience adds roughly **3 to 10 points** on SWE-bench-style coding benchmarks when it is verified, scoped and compact. Unfiltered or human-written skills average **close to zero**: 92 of 98 public skills showed no significant effect in one paired study ([arXiv 2603.15401](https://arxiv.org/abs/2603.15401)). Shared memory is also a proven attack surface, with cross-session poisoning success of **81.7% on Claude Code** reported in a 2026 preprint ([arXiv 2609.13889](https://arxiv.org/abs/2609.13889)). My recommendation is to build product (a), the error index, first and deliver it over MCP. Recall should fire only when an error actually occurs. Verification should count as the admission ticket for any entry, and you should treat it as a security property. Product (b), skill emergence, should grow out of the index later, through promotion of fix clusters that recur across repositories. Before writing much code, mine two to four weeks of a design partner's existing agent transcripts to measure how often the same error signature recurs across people. That single number decides whether the company exists.

## Every vendor ships memory; none ships a cross-vendor verified fix index

The competitive map has four layers. None of them combines all three of the product's ingredients: normalized error keys, outcome verification, and cross-vendor reach.

**Platform-native memory is now table stakes, and each vendor keeps it walled in.** GitHub Copilot Memory reached public preview on all paid plans on 2026-01-15 ([GitHub changelog](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/)). Its design is the reference spec buyers will hold you to. Each memory stores a fact, citations to code locations, and a reason. The agent re-checks the cited code before using the memory and corrects or refreshes it. Memories are shared across Copilot's coding agent, CLI and code review. Only users with write access can create them ([GitHub blog](https://github.blog/2026-01-09-building-an-agentic-memory-system-for-github-copilot)), and they expire after 28 days ([VS Code docs](https://code.visualstudio.com/docs/copilot/agents/memory)). GitHub reports that coding-agent PR merge rates rose from **83% to 90%** with memory. That figure is GitHub's own and has not been independently checked. Claude Code's auto memory is **machine-local and not shared across machines** ([Claude Code docs](https://code.claude.com/docs/en/memory)). Cursor Memories are personal. Cursor's Bugbot Learned Rules is the strongest example of automatic rule emergence with promote and demote signals: it drafts candidate rules from PR reactions, promotes those that gain signal, and disables stale ones ([Cursor changelog](https://cursor.com/changelog/04-08-26)). It covers code review only. Devin auto-suggests org-level Knowledge entries from feedback, but its Playbooks are written by hand ([Devin docs](https://docs.devin.ai/onboard-devin/knowledge)). Windsurf memories are local to a workspace, and team sharing is still a feature request ([Product Hunt thread](https://www.producthunt.com/p/windsurf/memories-are-cool-memories-with-friends-would-be-even-cooler)). Codex memory reportedly is off by default and belongs to one user, but that comes only from secondary sources, one of them the competitor Mem0 ([Mem0 blog](https://mem0.ai/blog/how-memory-works-in-codex-cli)).

**Error-tracking incumbents own fingerprinting and fix generation for production errors.** Sentry is the most dangerous adjacent player. It already groups errors with a fine-tuned stack-trace embedding model ([Sentry blog](https://blog.sentry.io/enhancing-issue-grouping)). Its Seer feature generates root causes and fix plans, and it hands those plans to Claude Code or Cursor over MCP ([Sentry blog](https://blog.sentry.io/seer-mcp-cli-or-coding-agent/)). Datadog's Bits AI Dev Agent auto-opens fix PRs for high-impact crashes ([Datadog blog](https://datadoghq.com/blog/bits-ai-dev-agent)). Both tie fixes to individual production issues. Neither builds a reusable signature-to-fix knowledge base, and neither covers the **dev-time errors** agents hit constantly: compiler, test, lint, dependency and environment failures. That gap is where the startup should play.

**Enterprise knowledge platforms already reach coding agents over MCP.** Stack Internal's MCP server reads and writes curated, voted Q&A. It supports Claude Code, Cursor, Copilot, Devin and others, and it enforces permissions and logs every request ([Stack quickstart](https://support.stackenterprise.co/support/solutions/articles/22000294548-mcp-server-quickstart-guide)). Unblocked sells an MCP "context engine" built on PR history ([Unblocked docs](https://docs.getunblocked.com/unblocked-mcp/mcp-overview)). Humans write the content on both platforms. If Stack Internal began ingesting agent sessions, it would become a direct competitor with trust signals already in place.

**Memory startups and open source are crowding the generic "shared memory" category.** Mem0 raised $24M in October 2025 ([BuiltIn](https://builtin.com/articles/mem0-raises-24m-AI-memory-infrastructure-20251103)). Supermemory and Vectorize Hindsight ship coding-agent plugins, including per-repo containers and team-memory skills ([Supermemory](https://supermemory.ai/blog/claude-code-memory-rehab/)). The YC 2026 cohort includes Skillsync, "GitHub for agent sessions" ([YesPress](https://yespress.io/skillsync-yc-w26)), and Wato, shared memory and workflows across a company ([neuronfeed](https://neuronfeed.com/startups/wato)). Both funding figures are about $500K and come from aggregators. SageOx raised a $15M seed for "agentic context infra for human-AI engineering teams" and is the closest funded comparable ([TAMradar](https://www.tamradar.com/funding-rounds/sageox-seed-15m)). Relai raised $5.4M to turn production failures into replayable environments and check fixes for regressions, which is conceptually the nearest neighbor to "verified fix" ([The Deep Feed](https://www.thedeepfeed.ai/posts/2026-06-12-agent-memory-seed-wave/)). The long tail of open-source MCP team-memory servers includes one with Bayesian confidence scoring and temporal decay ([team-memory-mcp](https://github.com/gustavolira/team-memory-mcp)). That tail shows demand. It also shows that **storage and retrieval alone have no moat**.

## Papers show reuse works only when verified, scoped and small

Research on agents reusing experience moved through three generations. Before 2024, agents replayed raw trajectories, like Reflexion's verbal self-critiques ([arXiv 2303.11366](https://arxiv.org/abs/2303.11366)). Next came induced, reusable programs and workflows. Voyager's executable Minecraft skill library unlocked tech-tree milestones up to **15.3x faster** ([arXiv 2305.16291](https://arxiv.org/abs/2305.16291)). Agent Workflow Memory raised WebArena success **51.1%** in relative terms ([arXiv 2409.07429](https://arxiv.org/abs/2409.07429)). Agent Skill Induction showed that skills written as verified programs beat skills written as text by **11.3%**, and its authors credit the gap mainly to verification ([arXiv 2504.06821](https://arxiv.org/abs/2504.06821)). The current generation maintains curated "playbooks" and SKILL.md folders that evolve over time.

On coding tasks specifically, the gains are real and moderate. ReasoningBank distills lessons from both successes and failures. It lifted SWE-bench Verified from **34.2 to 38.8** with Gemini-2.5-flash and from **54.0 to 57.4** with Gemini-2.5-pro, using fewer steps ([ReasoningBank HTML](https://arxiv.org/html/2509.25140v2)). Agent KB shares trajectories across agent frameworks and added **4.0 points** to OpenHands on SWE-bench ([arXiv 2507.06229](https://arxiv.org/abs/2507.06229)). MemGovern turned 135K GitHub issues and PRs into "experience cards" and added **4.65%** ([arXiv 2601.06789](https://arxiv.org/abs/2601.06789)). The most relevant 2026 preprint for this product is XRepoSkill. It compares successful and failed trajectories on the same issue, keeps a rule only if it is associated with success **and recurs across several repositories**, and merges repo-specific variants. The authors report **+10.3 points** on DeepSWE over no skills, across three vendors' models ([arXiv 2609.36807](https://arxiv.org/abs/2609.36807)). Treat every 2026 number in this report as an author claim from an abstract: none of those papers had peer review, and the PDFs were not checked.

Three results matter most for product design. The first is that **format matters more than retrieval**. REM found that injecting the same experience as a summary or a raw trajectory did not help, even when the right memory was retrieved perfectly. A compact, phase-structured document about 100x smaller than the trajectory, released only once the agent was struggling, raised resolution from 24.9% to 27.6% at 17% lower cost ([arXiv 2610.27377](https://arxiv.org/abs/2610.27377)). The second is that **small beats big**. In SkillsBench, curated skills raised average pass rates from 33.9% to 50.5%, and focused skills of at most three modules beat larger bundles ([arXiv 2602.12670](https://arxiv.org/abs/2602.12670)). Loading a skill body raises episode tokens by about 50% ([arXiv 2610.04832](https://arxiv.org/abs/2610.04832)). The third is that **strong-to-weak transfer is the most reliable sharing pattern**. Skills distilled from a stronger model's traces lift weaker executors: up to 54.3% in SkillWeaver ([arXiv 2504.07079](https://arxiv.org/abs/2504.07079)) and 4.5 to 18.8 points in Zep's production service, mostly on tasks the teacher had solved ([arXiv 2611.01386](https://arxiv.org/abs/2611.01386)). In a company, this means the hard-won fix from your best engineer's session becomes cheap help for everyone else's agent.

### Negative transfer is measured, common and invisible to completion metrics

Bad memories hurt, and they often hurt quietly. Agents tend to *follow* retrieved experience when a task looks similar, so a single wrong entry propagates ([arXiv 2505.16067](https://arxiv.org/abs/2505.16067)). On 36.78% of SkillsBench tasks, the same skill helped some model-harness combinations and hurt others ([arXiv 2610.08875](https://arxiv.org/abs/2610.08875)). Harmful skills cost up to **17 points** because they anchor the agent on their own template and override the task's instructions ([arXiv 2603.15401](https://arxiv.org/abs/2603.15401)). An analysis of 307 skill-induced failures found that most came from *seemingly relevant* skills, and the largest category was "excessive procedure," where a checklist turns into mandatory busywork ([arXiv 2608.11888](https://arxiv.org/abs/2608.11888)). The scoping result is the most damning for "share everything" designs. On a 12-round code-repair stream, a global memory of accepted skill edits scored **0.713, below the 0.775 of an agent with no memory at all**, with harmful deployments in 6 of 8 cases. Scoping each skill to the task family that produced it raised utility to 0.816, with zero harmful deployments ([arXiv 2609.29144](https://arxiv.org/abs/2609.29144)). Similar co-installed skills hijack about one run in five and silently drop core functions. Task completion does not change, so standard benchmarks miss the damage ([arXiv 2610.11647](https://arxiv.org/abs/2610.11647)).

Staleness behaves the same way. Sixteen LLMs rarely re-verified a constraint that read as settled and made stale-consistent decisions in about 75% of episodes ([arXiv 2608.25553](https://arxiv.org/abs/2608.25553)). When cached error-recovery fixes carried version stamps and invalidation hints, models complied with those hints anywhere from 100% of the time (Haiku 4.5) to 11% or less (Sonnet 5) ([arXiv 2609.00243](https://arxiv.org/abs/2609.00243)). The design lesson is concrete: **enforce freshness on the server; never ask the model to honor it.** One counterpoint deserves attention. Cortex keeps a learned change only if paired runs with and without it show a net gain. It found the gains shrank under a stronger model, and on a real open-source project it **found nothing to learn** ([arXiv 2610.14216](https://arxiv.org/abs/2610.14216)). Stronger frontier models erode the value of generic lessons. What they cannot know is your company's private build quirks, internal libraries and environment traps. The product's value lives in that proprietary tail.

## Shared memory is a writable attack surface, so verification doubles as security

A company-wide error index writes into every teammate's agent context, which makes it a prime target for prompt injection. The attack literature is mature. PoisonedRAG reached **90% attack success with five injected texts** in a database of millions ([arXiv 2402.07867](https://arxiv.org/abs/2402.07867)). AgentPoison exceeded 80% at a poison rate below 0.1% ([arXiv 2407.12784](https://arxiv.org/abs/2407.12784)). MINJA showed that any ordinary user can poison shared memory through queries alone ([arXiv 2503.03704](https://arxiv.org/abs/2503.03704)). The coding-specific preprints are sharper still. PMPA wrote malicious instructions from benign-looking external sources into persistent memory and reported **81.7% cross-session attack success on Claude Code** ([arXiv 2609.13889](https://arxiv.org/abs/2609.13889)). Across 24 configurations, malicious memory persisted in 84.2% of cases ([arXiv 2607.27080](https://arxiv.org/abs/2607.27080)). In a pooled same-team vector store, incidental cross-user leakage hit 70 to 100% ([arXiv 2610.04195](https://arxiv.org/abs/2610.04195)). The skill supply chain looks similar. Of 31,132 skills analyzed, **26.1% had at least one vulnerability** ([arXiv 2601.10338](https://arxiv.org/abs/2601.10338)). Snyk found that 13.4% of 3,984 marketplace skills had critical issues and confirmed 76 as malicious ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)).

The defense evidence points one way: **structure beats content screening**. A write-time screen with 0.832 recall on prompt injection rejected **0 of 360** poisoned memories that were simply false statements ([arXiv 2608.21230](https://arxiv.org/abs/2608.21230)). Pretext evaded skill scanners up to 97% of the time by moving payloads into natural language spread across files ([arXiv 2609.39607](https://arxiv.org/abs/2609.39607)). Three structural measures work. Hard ownership gating applied after retrieval restored baseline leakage at about 1.4 ms per query ([arXiv 2610.04195](https://arxiv.org/abs/2610.04195)). A gate on declared source type cut false adoption to 0.06 to 0.09, against 0.22 to 0.47 for other policies ([arXiv 2609.30813](https://arxiv.org/abs/2609.30813)). Consensus validation across related memories cut attack success by more than 95% ([arXiv 2510.02373](https://arxiv.org/abs/2510.02373)). Execution provenance raised joint success on skill-lifecycle tasks from 49% to 66% ([arXiv 2610.35215](https://arxiv.org/abs/2610.35215)). For this product, the implication is a selling point. An entry admitted only because a real test or CI run turned green, carrying signed provenance about who, which session, which commit and which agent produced it, and retrievable only inside the tenant and repository scopes that certified it, is both **higher quality and harder to poison**. Store fixes as references to diffs and commits rather than as free-text instructions, and cap how much context any one source can occupy. Copies of skills almost never pick up upstream fixes, which is another reason to prefer versioned references over copies ([arXiv 2610.11169](https://arxiv.org/abs/2610.11169)).

## Crash-triage engineering already solved most of the error index

The founder does not need to invent signature matching. Crash-reporting systems have refined it for 15 years, and the pattern is consistent. Production systems first compute a cheap deterministic fingerprint, then fall back to learned similarity behind a conservative threshold, and they **bias against wrongly merging distinct errors**. A wrong merge attaches the wrong fix, which is worse than a missed match. Here is how each technique applies.

**Normalization: turn noisy messages into stable templates.** Mask the parts that vary between occurrences: paths, line numbers, hex addresses, IDs, timestamps. This is the log-parsing problem, and the Drain parser is the fast classical baseline ([logpai/logparser](https://github.com/logpai/logparser/blob/master/logparser/Drain)). LILAC adds an LLM that is called only when a message misses a template cache. It beat the prior state of the art by 66.8% on grouping F1 and ran at speeds comparable to Drain ([arXiv 2310.01796](https://arxiv.org/pdf/2310.01796)). LILAC's architecture, a cache of templates with an LLM only on a miss, is the same shape as an error index. Mozilla's Socorro shows how to choose which stack frames matter. Rule lists skip "irrelevant" frames such as panic handlers and merge "prefix" frames with the next frame ([Socorro docs](https://socorro.readthedocs.io/en/latest/signaturegeneration.html)). The same trick applies to skipping test-runner, framework and assertion-library frames. A practical signature for dev-time errors combines the tool, the error code (such as `TS2345` or `E0382`), the masked message template, the exception type, and the top few in-project frames in order. That recipe is my inference: no benchmark covers normalization of compiler or CI messages specifically. Keep the masked values, such as the missing symbol or the file, as fix parameters rather than discarding them.

**Similarity: generic text embeddings are weak for stack traces; fine-tune or use frame-aware scoring.** An embedding turns text into a vector so that similar items sit close together. HNSW is the standard fast index for finding nearest vectors. Sentry's v2 grouping fine-tuned `modernbert-embed-large` on hundreds of thousands of stack-trace pairs labeled by Claude Sonnet 4.5 and checked against expert labels. It cut wrong merges from **8% to 4%**, raised new issues prevented from 50% to 70%, and brought lookups to **12 ms** at p50 ([Sentry blog](https://blog.sentry.io/enhancing-issue-grouping)). Sentry says stack-trace grouping is "not the kind of task embeddings APIs are trained to handle." The dedupT paper similarly found an off-the-shelf OpenAI-embedding-plus-GPT-4o pipeline performed poorly ([arXiv 2508.19449](https://arxiv.org/pdf/2508.19449)). Both claims are snippet-level. Cheaper classical methods remain competitive. Microsoft's ReBucket weights matching frames by closeness to the top of the stack and reached an F-measure around 0.88 across five products ([ReBucket PDF](https://s-cube-xmu.github.io/uploads/ReBucket.pdf)). JetBrains' TraceSim combines frame weights with edit-distance alignment and runs in production triage ([arXiv 2009.12590](https://arxiv.org/pdf/2009.12590)). An older study even found plain tf-idf beat purpose-built crash bucketing on Ubuntu data ([PeerJ](https://peerj.com/preprints/1705)). Deterministic rules alone over-split. Microsoft talk material suggests one bug can scatter across several buckets for up to 40% of Windows error reports, a snippet-level figure from slides ([slides](https://api.sambuz.com/doc/ten-years-of-ppt-presentation-721048)). The recommended layering is an exact-signature lookup first, then a frame-aware or fine-tuned similarity fallback with a high threshold, then an LLM judge on borderline cases.

**Retrieval of fixes: the industrial precedent is strong.** Google's DeepDelta learned from developer build-fix pairs and correctly repaired **about 50% of unseen Java build errors**, with the correct fix in the top three 85 to 87% of the time ([Google Research](https://research.google/pubs/deepdelta-learning-to-repair-compilation-errors/)). Google later fine-tuned DIDACT on "resolution sessions," the sequence of workspace snapshots from first breakage to green build. An 11-week randomized trial showed **about 2% gains in coding time and change throughput**, with about 34% of affected developers applying a fix and no detectable rise in rollbacks ([Google Research blog](https://www.research.google/blog/safely-repairing-broken-builds-with-ml)). An agent session that moves from a failing build or test to a passing one is exactly a resolution session, so your harvest unit already has a proven template. Error distributions are heavily skewed: **51% of Google's compiler diagnostics were unresolved-symbol errors** ([Google Research](https://research.google/pubs/pub47999/)). A small head of signatures will cover most lookups. The tail is harder. On CI-Repair-Bench, the best LLM agent repaired only **18.9%** of real CI failures, and environment and dependency failures were the hardest category ([arXiv 2604.27148](https://arxiv.org/pdf/2604.27148)). Those failures are also the most company-specific, which makes them the place a verified index adds the most value that models cannot. Meta's Getafix mined abstract fix templates from multiple human fixes of the same pattern ([arXiv 1902.06111](https://arxiv.org/abs/1902.06111)). Once several fixes share a signature, the same approach yields a parameterized template that survives code drift better than a literal diff.

**Commit-aware staleness: no paper studies it directly, so borrow from build caching and test selection.** Store with each fix the commit SHA, content hashes of the touched spans or symbols, lockfile and toolchain versions, and the error's in-project frames. On lookup, compare against the current HEAD. An exact match means fresh. Changes only to unrelated files mean probably valid. A changed touched file, symbol or dependency version means demote and re-verify. This design is my inference. The closest evidence is Meta's predictive test selection: a learned model caught **over 99.9% of faulty changes while running under a third of the tests** that dependency analysis would select ([arXiv 1810.05286](https://arxiv.org/pdf/1810.05286.pdf)). It argues for a learned relevance score over hard invalidation on every dependency edge. Combine that score with Copilot-style re-checking of cited code at use time, and with decay.

**Verification signals: build an outcome ladder and discount flaky evidence.** Rank each signature-fix pair by the strongest evidence it has earned. From weakest to strongest, the ladder runs: the error stops reproducing, targeted tests pass, full CI goes green, the PR merges, the change is not reverted within N days, and the signature does not recur. This ladder is my synthesis, modeled on Google's multi-stage safety pipeline and its rollback guardrail ([Google Research blog](https://www.research.google/blog/safely-repairing-broken-builds-with-ml)). Flakiness is the main confound: in 2016 Google reported that almost 16% of its tests had some flakiness ([Google Testing Blog](https://testing.googleblog.com/2016/05/)). Choosing among competing fixes for one signature is a natural fit for Thompson sampling. In plain terms, each fix keeps a running success estimate that outcomes update, and the system mostly serves proven fixes while occasionally trying newer ones. No source reports this applied to fix indexes, so it is an inference.

**Skill extraction, merging and maintenance: promote by recurrence, update by delta, retire carefully.** The best-supported pipeline for product (b) runs as follows. Cluster verified fixes and session traces. Compare successful and failed attempts on the same problem to find where they diverge ([XRepoSkill](https://arxiv.org/abs/2609.36807)). Admit a skill only when a paired with/without test shows net gain and no task regresses ([Cortex](https://arxiv.org/abs/2610.14216); [EvoSkill](https://arxiv.org/abs/2603.02766)). Keep it scoped to its originating repo or family until it recurs elsewhere. Private memory stays private, and only "widely proven" ideas are shared ([CoMem](https://arxiv.org/abs/2609.15009); [HiPS](https://arxiv.org/abs/2608.25329)). Edit skills with incremental deltas, because full rewrites cause "context collapse" ([ACE](https://arxiv.org/abs/2510.04618)). Prune periodically: TroVE's toolboxes ended up 79 to 98% smaller with better accuracy ([arXiv 2401.12869](https://arxiv.org/abs/2401.12869)). Be careful when retiring a skill for showing near-zero gain. That can mean "the model already does this" or "nobody can do this," and 28 of 31 SkillsBench retirements rested on probes no run passed ([arXiv 2610.32322](https://arxiv.org/abs/2610.32322)). The literature does not settle merge strategy, whether to LLM-merge, union, or keep both versions. Detect duplicates at install time and check for conflicts at first read ([arXiv 2610.11647](https://arxiv.org/abs/2610.11647)).

## Multi-vendor use creates the seam, and native memory threatens to close it

The demand case rests on one solid data point and one unmeasured hypothesis. The solid point is multi-tool use. In the Pragmatic Engineer's 2026 survey of 906 engineers, **70% use two to four AI tools** and 15% use five or more. Claude Code leads at small companies, while Copilot (56%) leads at companies with 10,000+ employees ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/ai-tooling-2026)). A fix one engineer's Claude Code session discovers is invisible to a teammate's Copilot or Codex session. That is the neutral layer's reason to exist. Trust data supports verification as the pitch. In secondary reporting of the 2026 Stack Overflow survey, 78.7% of developers called attribution important, and nearly half trust AI output only when they can verify it ([IT Brief UK](https://itbrief.co.uk/story/stack-overflow-survey-shows-developers-trust-ai-with-caveats)). Only 24% of respondents said their employer had published formal AI guidance, so governance buyers exist but are immature. The likely buyer is a platform or DevEx team.

The unmeasured hypothesis is the core thesis: **agents across a company repeatedly rediscover the same fixes.** No public study measures redundancy across sessions or teammates. The closest data is a small pilot of 9 transcripts, which found re-exploration within a session averaged **10.9%** of exploration calls (range 0 to 29.1%), clustered at context-compaction boundaries ([arXiv 2607.20972](https://arxiv.org/pdf/2607.20972)). Read operations consumed **76.1% of tokens** in one SWE-bench setup ([arXiv 2601.16746](https://arxiv.org/pdf/2601.16746)). Snowflake's engineering blog reports that about a quarter of agent turns were "pure rediscovery" before it built team-owned "Experience Cards" ([Snowflake blog](https://www.snowflake.com/en/blog/engineering/ai-agent-memory-experience-cards/)). That is the best practitioner signal, but it is a single company's self-report. Practitioner complaints focus on CLAUDE.md being forgotten as context fills and on LLM-written AGENTS.md files adding "context rot" ([HN](https://news.ycombinator.com/item?id=49815527)). Those complaints argue for recall that is **triggered by errors and kept small**, not for more context loaded at startup. Treat the economics with care. Claude Code spend of roughly **$150 to 250 per developer per month** is an unverified vendor-blog attribution ([Morph](https://www.morphllm.com/ai-coding-costs)). Even a 10% cut in waste is worth only $15 to 25 per engineer per month, so token savings alone cap the price. Price on time-to-green and first-try success instead. Benchmarks for pricing are $32 to 40 per seat for Cursor Teams and Bugbot's move to usage-based billing ([Cursor pricing](https://cursor.com/docs/account/teams/pricing)). That suggests about $10 to 20 per active engineer per month or a platform fee. This is not benchmarked directly.

Platform risk is high and already arriving. GitHub says other agents are "expected to follow" Copilot's shared memory ([GitHub blog](https://github.blog/2026-01-09-building-an-agentic-memory-system-for-github-copilot)), and moving from repo scope to org scope is the obvious next step. Anthropic redesigned Claude Code Projects around September 2026 so that parallel sessions read and write a shared memory, with Team and Enterprise to follow ([VentureBeat](https://venturebeat.com/orchestration/anthropic-launches-claude-code-projects-an-always-on-conversation-that-remembers-and-delegates-your-long-running-dev-work)); reported dates were inconsistent. Sentry has fingerprints, fix generation and an MCP pipe into agents. One step from "this fingerprint was fixed before, and the deploy confirmed it" would put it in your lane for runtime errors. The strongest counter-argument is structural. Vendors have no incentive to share learnings with each other, enterprises are wary of a model provider holding their institutional knowledge ([The Deep Feed](https://www.thedeepfeed.ai/posts/2026-06-12-agent-memory-seed-wave/)), and multi-vendor use is the norm. Data access has its own fragility. Claude Code's local JSONL transcripts are documented as an internal format subject to change. Its OpenTelemetry export redacts prompts, responses and tool content by default unless admins opt in through managed settings ([Claude Code docs](https://code.claude.com/docs/en/monitoring-usage)). Codex and Cursor transcript access was not verified. The robust answer is to make **the agent itself the reporter**, through MCP tools it calls, and to use transcripts and telemetry as secondary sources.

## The wedge: a verified, cross-vendor index of dev-time errors, sold as safe

The differentiated wedge sits where three facts meet. First, native vendor memory is siloed and mostly unverified, and Claude Code explicitly excludes debugging fixes. Second, error-tracking incumbents own production errors but not the build, test, lint, dependency and environment failures agents hit every hour. Third, the research says shared experience helps only when it is verified, scoped and compact, and it is dangerous otherwise. The defensible product is therefore **"an org's verified fix memory for dev-time errors, usable by any coding agent, where nothing enters without a green test or CI run and nothing leaves its permission scope."** Verification, scope and provenance are the product. Storage is a commodity. I would deliberately not lead with skill emergence. SWE-Skills-Bench's 92-of-98 null result, the global-memory-below-baseline finding, and the 50% token cost of loading skill bodies all show that a weak skill product is worse than none. The error index also has a crisp key (the signature), a crisp trigger (an error appeared), and a crisp success test (the error disappeared and tests passed). Skills should come later as a promotion tier: a cluster of verified fixes that recurs across repositories graduates into a small, scoped SKILL.md, admitted only after a paired evaluation. The SKILL.md format has converged across harnesses and research systems ([arXiv 2611.01386](https://arxiv.org/abs/2611.01386)), so those skills stay portable.

### A four-part MVP that a small team can ship in one quarter

The MVP has four parts. The first is an **MCP server with two tools**: `lookup_error(raw_error, repo, commit)` and `report_fix(signature, diff_ref, evidence)`. Distribute it through the MCP registry and enterprise gateway allowlists, not public skill marketplaces ([Portkey](https://portkey.ai/docs/aigw/product/mcp-gateway/mcp-registry); [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)). Where a harness supports hooks, add a lightweight hook that calls the lookup automatically when a build or test command exits non-zero, so recall does not depend on the model remembering to ask. The second is a **signature engine**: regex masking, Socorro-style frame rules for common stacks (start with TypeScript/Node, Python and one JVM language), exact-key lookup, and a frame-aware similarity fallback with a high threshold tuned against wrong merges. Fine-tune an embedding model later, once you have labeled pairs. Use LLM labels spot-checked by humans, the way Sentry does. The third is a **verification and staleness ledger**. Each entry records the outcome-ladder level it has reached, the commit, touched-file hashes and toolchain versions. The server, not the model, demotes an entry on drift and discounts flaky tests. The fourth is **governance from day one**: tenant and repo ownership gating applied after retrieval, signed provenance (user, session, agent, commit), fixes stored as diff references rather than free-text instructions, a cap on how much context any one source can occupy, a review queue before any entry crosses from repo scope to org scope, and an audit log. Return format follows REM: a short, structured "signature → what fixed it → evidence → caveats" card, never a raw transcript.

### Validate the thesis with one number before building the product

| Phase | What you do | Go/no-go signal (proposed thresholds, not sourced) |
|---|---|---|
| 0. Offline mining (2–4 weeks) | Get existing JSONL transcripts or OTel exports from 3–5 design partners running multiple agents; normalize every error; find failing→green "resolution sessions" | Cross-person duplicate-signature rate: the share of error occurrences whose signature was already resolved by someone else in the org. Proceed if roughly 15%+ of non-trivial errors recur across people and time-to-green on those is material |

| 2. Paired live test (6–8 weeks) | Randomize recall on/off per error occurrence, Google-RCT style | Time and tokens from first error to green; first-try success; acceptance rate; and a harm rate (recalled fix was wrong, reverted or misled) that does not exceed the off arm |
| 3. Skill promotion pilot | Promote cross-repo recurring clusters into scoped skills; paired with/without runs on mined-PR tasks | Net gain with zero regressed task families; watch token cost and "excessive procedure" |

The ROI baseline already exists in vendor telemetry: Claude Code emits cost, token, active-time, session and commit metrics ([Claude Code docs](https://code.claude.com/docs/en/monitoring-usage)). Be honest about variance. The "Skill Issue" study found that per-repository gains from optimized skills could not be separated from run-to-run noise at single-repo scale ([arXiv 2609.12742](https://arxiv.org/abs/2609.12742)). Pool across repositories and run repeated trials before claiming wins. A publishable "duplicate-subproblem rate" from real team logs would be a marketing asset on its own, because nobody has measured it publicly.

## Conclusion

The founder should change one framing. In this market, "shared memory" is a commodity, and the labs are increasingly giving it away free. Unverified shared memory is also something buyers will rightly fear as an injection channel. The scarce asset is an evidence ledger: which fix, for which normalized error, at which commit, under which toolchain, verified by which green run, and allowed to reach which people. That ledger is what makes recall precise, staleness enforceable, poisoning expensive, and skills safe to promote. A vendor can copy a memory feature in a quarter. It is much harder for any one vendor to become the neutral record of outcomes across Claude Code, Copilot, Codex and Cursor at once.

The biggest open risk is empirical, not competitive. If cross-person recurrence of dev-time errors turns out low, or frontier models increasingly fix those errors unaided, as Cortex's shrinking gains under a stronger model hint, the index shrinks to the company-specific environment and dependency tail. That tail may still be valuable, since it is exactly where CI-repair agents score worst. But the company would need to be sized and priced for it. Run the offline mining study first, and let that number decide between a venture-scale platform and a sharp, narrower tool.
